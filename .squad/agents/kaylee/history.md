- **CLI provider registration pattern:** Cloud providers follow consistent structure: (1) Create adapter class implementing IProviderAdapter with unique ID, (2) register as singleton in ProviderServiceCollectionExtensions via `services.AddSingleton<IProviderAdapter, YourAdapter>()`, (3) adapter constructor accepts IHttpClientFactory + SecretResolver + ConfigStore, (4) CheckAsync validates endpoint+apiKey availability, (5) GenerateAsync reads config/secrets, instantiates generator, calls GenerateAsync, saves result. RequiredFields = ["endpoint", "model"], RequiredSecrets = ["apiKey"].
- **Sample scenario structure:** All cloud API samples follow convention: (1) appsettings.json with placeholder values, (2) UserSecretsId in .csproj for secure credential storage, (3) Program.cs shows ConfigurationBuilder chain (UserSecrets > EnvVars > appsettings.json), (4) README.md documents three setup options (user secrets, env vars, appsettings.json) with Azure Portal instructions, (5) output/ directory for generated images. Samples are self-contained with project references to Foundry library.

- **CLI command implementation (2026-04-19):** Implemented all CLI commands (GenerateCommand, ConfigCommand, SecretsCommand, DoctorCommand, ProvidersCommand, VersionCommand) using Spectre.Console.Cli. GenerateCommand is wired as the default command via `CommandApp<GenerateCommand>`. All commands consume `ProviderRegistry`, `SecretResolver`, and `ConfigStore` from DI. Commands must request dependencies via constructor injection — Spectre.Console.Cli uses the custom `TypeRegistrar` to resolve them.
- **Spectre.Console rendering best practices:** Always use `Markup.Escape()` when interpolating user input (prompts, provider names, etc.) into markup strings to avoid Spectre markup injection. Use `AnsiConsole.MarkupLineInterpolated` for safe interpolation. Non-interactive detection via `ConsoleHelpers.IsInteractive()` checks both `Console.IsInputRedirected` and `AnsiConsole.Profile.Capabilities.Interactive`.
- **ProgressRenderer pattern:** Wrap Spectre.Console's `ProgressTask` in an `IProgress<GenerationProgress>` adapter. Use `ProgressRenderer.RunWithProgressAsync` static helper to run async work with a progress bar. This keeps progress reporting decoupled from Spectre.Console specifics.
- **InternalsVisibleTo for tests:** Test projects (Jayne's work) need access to `internal` command classes. Add `[assembly: InternalsVisibleTo("ElBruno.Text2Image.Tests")]` in `Properties/AssemblyInfo.cs` to expose internals without making classes public.
- **SecretResolver extensibility:** Added `SetAsync` overload without `preferredStoreName` parameter (delegates to the full overload with `null`). Also added `DeleteAsync` which removes secrets from all available stores (best-effort deletion to ensure complete removal).
- **Platform attribute requirements:** DPAPI-specific methods require `[SupportedOSPlatform("windows")]` attribute from `System.Runtime.Versioning` namespace. This attribute ensures compile-time checks for platform-specific code paths.

- **InitCommand pattern (2026-04-20):** Implemented `t2i init` command following Spectre.Console.Cli patterns. Uses embedded resource for SKILL.md content (added via `<EmbeddedResource Include="Skills\SKILL.md" LogicalName="ElBruno.Text2Image.Cli.Skills.SKILL.md" />`). Runtime loading via `Assembly.GetManifestResourceStream()`. Command writes to multiple targets (`.github/skills/t2i/SKILL.md`, `.claude/skills/t2i/SKILL.md`) based on `--target` flag (github/claude/all). `--force` flag controls overwrite behavior. Status output uses `AnsiConsole.MarkupLineInterpolated` with icon+color per target, plus final summary `Panel`.
- **Embedded resource workflow:** Add file to project, mark as `<EmbeddedResource>` with `LogicalName` attribute, load at runtime via `Assembly.GetManifestResourceStream(logicalName)`. Allows shipping non-code assets (skill files, templates, etc.) inside the compiled assembly without external file dependencies.

- **IProviderAdapter RequiredFields split (2026-04-20):** Split `RequiredSecrets` (sensitive, masked) from `RequiredFields` (non-sensitive, plain text). `IProviderAdapter` now defines both: `RequiredSecrets` returns apiKey-only for cloud providers; `RequiredFields` returns endpoint+model (default implementation `=> Array.Empty<string>()`). Both Foundry adapters (`FoundryMaiImage2Adapter`, `FoundryFlux2Adapter`) implement both properties. Adapters read endpoint/model from `ConfigStore` (via `config.Providers[Id]?.Endpoint` and `config.Providers[Id]?.Model`) with fallback to hardcoded defaults ("MAI-Image-2", "FLUX.2-pro"). Backward compat: endpoint also falls back to `SecretResolver` for existing users who stored it as a secret.
- **ConfigStore usage in adapters:** Both Foundry adapters now accept `ConfigStore` via constructor DI (wired in Program.cs). They call `await _configStore.LoadAsync(ct)` to read `ProviderConfig` values. This pattern allows adapters to access user-configured values (endpoint, model) without treating them as secrets. Model name flows to the generator constructor (already supported by `MaiImage2Generator` and `Flux2Generator`).
- **SetupWizard RequiredFields prompting:** After secrets loop, wizard iterates `provider.RequiredFields` and prompts for each. For "endpoint": prompt shows default `https://<your-resource>.services.ai.azure.com`, validates URL format, saves to `ProviderConfig.Endpoint`. For "model": determines default by provider ID (foundry-mai2 → "MAI-Image-2", foundry-flux2 → "FLUX.2-pro"), allows override, saves to `ProviderConfig.Model`. Changes are persisted via `ConfigStore.SaveAsync`.
- **ConfigCommand field routing:** `SetAsync` now checks three paths: (1) `RequiredSecrets.Contains(field)` → route to `SecretResolver`, (2) `RequiredFields.Contains(field)` → route to `ProviderConfig` (endpoint/model), (3) fallback → extras dictionary. `ShowAsync` displays RequiredFields from config (plain text), RequiredSecrets from secret store (masked). Fields shown as "[grey](not set)[/]" if missing.
- **DoctorCommand and ProvidersCommand updates:** Both now check `RequiredFields + RequiredSecrets` for "fully configured" status. Table columns show config status as fraction (e.g., "3/3" green, "1/3" yellow). Doctor shows both config fields and secrets in unified table with "Type" column (config vs secret).
